# 스프린트 계획 (생성 + 백로그 구성)

빈 스프린트만 만드는 `sprint init` 과 달리, 다음 스프린트를 만들고 백로그까지 채운다. 근거는 이번 주 스프린트 페이지의 **회고 회의노트**와 **백로그 DB 의 실제 상태** 두 가지뿐이다. 둘 다 조회하지 않고 항목을 지어내지 않는다.

- 리소스 ID·속성 맵·실행 규칙: [notion-resources.md](../../references/notion-resources.md). 조회·쓰기는 `bun ${CLAUDE_PLUGIN_ROOT}/scripts/ntn.ts`(이하 `ntn.ts`).
- 점수: [backlog-scoring](../backlog-scoring/SKILL.md) 의 rubric 을 그대로 적용한다.
- 이월 규칙·제목 형식·스프린트 생성 바디: [po](../po/SKILL.md).
- 용량 판단 근거: [scrum-playbook.md](../../references/scrum-playbook.md) 의 벨로시티·용량계획 절.
- 브리핑 작성은 이 스킬의 일이 아니다. 끝난 뒤 원하면 `sprint report` 를 이어서 돌린다.

진행 체크리스트 (응답에 복사해 체크한다):

```
- [ ] 0 인증·N 확인
- [ ] 1 날짜·중복·이번 주 스프린트
- [ ] 2 스프린트 생성
- [ ] 3 회고 읽기
- [ ] 4 백로그 실태 (전 페이지)
- [ ] 5 이월 판정
- [ ] 6 액션아이템 매핑
- [ ] 7 항목별 확인
- [ ] 8 반영 (batch)
- [ ] 9 용량 점검 (재조회)
- [ ] 10 제목 갱신
- [ ] 11 보고
```

## 절차

### 0. 인증·범위 확인

`ntn whoami < /dev/null` 로 인증을 확인한다. 인자 `N` 이 `1~4` 정수가 아니면 실행하지 않는다. 인자가 없으면 `1` 로 가정하지 말고 묻는다.

### 1. 날짜·중복·이번 주 스프린트

- `ntn.ts sprint-dates {N}` 으로 기간과 placeholder 제목을 얻는다.
- `ntn.ts sprints` 에 같은 시작일이 있으면 만들지 않고 알린 뒤 계속할지 묻는다.
- `ntn.ts current-sprints` 의 `current` 가 이번 주 스프린트다(2·3단계 근거). `null` 이면(스프린트 공백기) 후보를 보여 주며 확인한다.
- `untitled` 에 기간 없는 빈 행이 있으면 판정에서 빼고 보고에 한 줄로 알린다. 임의로 지우지 않는다.

### 2. 스프린트 생성

po 스킬 「스프린트 생성」 단계 3과 같은 바디로 만든다. 뒤이어 만들 백로그가 `⚡ 스프린트` relation 으로 이 페이지 ID 를 쓰므로 먼저 만들고, 응답의 `id` 를 기록한다.

### 3. 이번 주 회고 읽기

`ntn pages get <THIS_SPRINT_PAGE_ID> < /dev/null` 에서 세 곳을 본다.

- `## 백로그 회고` / `## 스프린트 리뷰` meeting-notes 의 `<summary>`: 액션 아이템, 이슈, "다음주 계획". 다음 스프린트 항목의 1차 출처다.
- `## 이월/취소 기록` 절(있으면): 이미 처리된 이월 내역.
- 본문 상단 브리핑(있으면): 이번 주에 하기로 했던 일.

`<summary>` 가 `<empty-block/>` 뿐이면 회고 근거가 없다. 이월 항목만 만들고, 신규 항목은 "회고가 비어 있어 신규 항목 근거가 없어요" 라고 알린 뒤 마스터에게 직접 받는다.

### 4. 백로그 실태 조사

- 이번 주 스프린트 백로그: `ntn.ts backlog --sprint <THIS_SPRINT_PAGE_ID>`
- 백로그 전체: `ntn.ts backlog --json > <작업 디렉터리>/backlog_all.json`. 스크립트가 전 페이지를 받는다. 직접 `ntn datasources query` 를 부르면 25건에서 잘린다.

이 덤프에서 세 가지를 뽑는다.

- **미완료 목록**: 이번 주 백로그 중 `완료`·`취소` 가 아닌 것 → 5단계 대상.
- **고아 항목**: 상태가 `완료`·`취소`·`제품` 이 아닌데 `sprint` 가 빈 것. 6단계 전에 마스터에게 알리고 처리를 고르게 한다(완료 처리·스프린트 연결·제품으로 되돌림).
- **작업자 ID 맵**: `people` 의 이름→ID. 덤프에 없는 사람은 추측하지 말고 비워 두고 묻는다.

### 5. 이월 판정

미완료 항목마다 po 스킬 「백로그 이월 규칙」의 상태별 기본 처리를 적용한다. 원본의 `⚡ 스프린트` relation 은 어떤 경우에도 바꾸지 않는다.

- 잔여 범위는 회고에서 근거를 찾는다. 회고 액션아이템이 원본 한 건을 두 갈래로 쪼개면 두 건으로 나눈다(예: "정산정보 수집·계산 로직" → "Toss 정산 불일치 수정" + "KICC 정산 추가"). 근거가 없으면 묻는다.
- 마스터 지시가 기본 처리와 다르면 지시를 따르되, 전례와 어긋난다는 점을 한 줄로 알린다.

### 6. 회고 액션아이템 → 백로그 매핑

액션 아이템과 "다음주 계획"을 한 건씩 4단계 덤프와 대조한다. 제목 문자열이 아니라 **내용**이 같으면 같은 일이다. 애매하면 후보를 보여 주며 묻는다. 이미 `[x]` 로 닫힌 액션아이템은 뺀다.

- 이미 있고 `제품` → `스프린트` 로 바꿔 새 스프린트에 연결. 점수는 건드리지 않는다.
- 이미 있고 `스테이징`·`진행 중` → 5단계 이월 판정으로 넘긴다.
- 없음 → 신규 생성.

### 7. 항목별 확인

신규 항목은 **한 건에 질문 하나로, 순차로** 묻는다. 앞 답이 뒤 판단을 바꾸므로 묶지 않는다. 질문마다 작업 이름·선제조건·완수조건을 보이고, 선택지에 "추가 안 함" 과 "두 건으로 분리" 같은 실제 대안을 넣는다.

이미 등록·스코어링된 항목을 고르기만 하는 경우(제품→스프린트)는 `multiSelect` 로 한 번에 물어도 된다.

작업 이름은 "{목적}을 위해, {행위}한다" 형식이다. `[스파이크]`·조사 항목은 점수를 공란으로 둔다.

### 8. 반영 (batch)

승인된 내용을 Write 도구로 ops 파일 하나에 담아 `ntn.ts batch <ops.json>` 으로 반영한다. 순서는 신규 생성 → 제품→스프린트 이동 → 이월 원본 `지연사유` 다. `상태` 를 바꾸는 항목은 바꾸기 전 값을 보고에 남긴다.

```json
[
  {
    "label": "신규: <작업 이름>",
    "path": "/v1/pages",
    "method": "POST",
    "body": {
      "parent": {"type": "data_source_id", "data_source_id": "a07f68d9-4082-8359-9579-07c5578db49e"},
      "properties": {
        "작업 이름": {"title": [{"text": {"content": "<작업 이름>"}}]},
        "상태": {"status": {"name": "스프린트"}},
        "⚡ 스프린트": {"relation": [{"id": "<NEW_SPRINT_PAGE_ID>"}]},
        "에픽": {"relation": [{"id": "<EPIC_ID>"}]},
        "작업자": {"people": [{"object": "user", "id": "<USER_ID>"}]},
        "작업크기": {"select": {"name": "3"}},
        "비즈니스가치": {"select": {"name": "5"}},
        "긴급도": {"select": {"name": "3"}},
        "위험도": {"select": {"name": "2"}},
        "가치판단": {"rich_text": [{"text": {"content": "<backlog-scoring 형식>"}}]}
      },
      "children": [
        {"type": "heading_2", "heading_2": {"rich_text": [{"text": {"content": "배경"}}]}},
        {"type": "paragraph", "paragraph": {"rich_text": [{"text": {"content": "<배경>"}}]}},
        {"type": "heading_2", "heading_2": {"rich_text": [{"text": {"content": "완료 조건"}}]}},
        {"type": "paragraph", "paragraph": {"rich_text": [{"text": {"content": "<완료 조건>"}}]}},
        {"type": "heading_2", "heading_2": {"rich_text": [{"text": {"content": "참고"}}]}},
        {"type": "paragraph", "paragraph": {"rich_text": [{"text": {"content": "<원 항목 URL>"}}]}}
      ]
    }
  },
  {
    "label": "이동: <작업 이름>",
    "path": "/v1/pages/<BACKLOG_PAGE_ID>",
    "method": "PATCH",
    "body": {"properties": {
      "상태": {"status": {"name": "스프린트"}},
      "⚡ 스프린트": {"relation": [{"id": "<NEW_SPRINT_PAGE_ID>"}]}
    }}
  },
  {
    "label": "지연사유: <작업 이름>",
    "path": "/v1/pages/<ORIGINAL_PAGE_ID>",
    "method": "PATCH",
    "body": {"properties": {"지연사유": {"rich_text": [{"text": {"content": "<왜 못 끝냈는지> → <이월한 항목>"}}]}}}
  }
]
```

- 스파이크 신규 항목은 점수 4종과 `가치판단` 키를 빼고, `참고` 가 없으면 마지막 두 블록을 뺀다.
- 처음 돌릴 때는 `--dry-run` 으로 바디를 확인한 뒤 실제로 실행한다.
- `FAIL` 이 있어도 나머지는 진행된다. 실패 목록은 11단계 보고에 반드시 넣는다.

### 9. 용량 점검

반영 후 `ntn.ts backlog --sprint <NEW_SPRINT_PAGE_ID>` 로 다시 조회해 WIP 합계와 작업자별 포인트·건수를 집계한다.

- 직전 스프린트 WIP 보다 대략 1.5배 이상 늘었으면 수치를 들어 알린다. 우선순위가 가장 낮은 항목을 이름으로 지목해 제품 백로그로 내리는 안을 제시하고, 임의로 빼지 않는다.
- 한 사람에게 몰렸으면 그 사람의 포인트·건수를 보인다.
- 점수·에픽이 빈 항목(스파이크 제외)은 경고로 표시한다.

### 10. 제목 갱신

po 스킬 「스프린트 제목 정리」 단계 3~4로 placeholder 를 교체한다. 승인 전에 바꾸지 않고, 이전 제목은 보고에 남긴다.

### 11. 보고

- 새 스프린트 제목·기간·URL, 백로그 건수·WIP
- 우선순위 내림차순 목록 (우선순위 · 크기 · 작업자 · 작업 이름)
- 한 일: 신규 N건 / 제품→스프린트 N건 / 지연사유 N건 / 이월하지 않은 스테이징 N건 / 고아 항목 처리
- 짚어둘 것: 용량 경고, 범위 미확정 항목, 실패한 쓰기. 없으면 없다고 쓴다.

## 주의

- 원본 백로그의 `⚡ 스프린트` relation 은 바꾸지 않는다.
- 생성한 백로그는 `ntn pages trash <page-id> --yes` 로 되돌린다. 상태 변경은 이전 값이 있어야 되돌릴 수 있다.
- 스프린트 페이지 본문 블록은 건드리지 않는다. `ntn pages edit` 는 회의노트를 망가뜨릴 수 있다.
- 회고에 근거가 없는 항목은 만들지 않는다.
