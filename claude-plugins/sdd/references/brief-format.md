# brief 포맷

`sdd:brief-dev`(개발자용)와 `sdd:brief-nondev`(비개발자용)가 함께 쓰는 단일 출처다. 두 스킬은 `sdd:draft` 가 쓴 요구사항 문서(requirements.md)를 받아, 결정 표기를 걷어 내 읽기 쉬운 기획 문서로 바꾼다. 새로 조사하거나 정하지 않는다. 요구사항 문서가 원본이고, brief 는 그 원본에서 뽑아낸 사본이다.

brief 문서는 한 장으로 끝난다. 길어져도 다른 파일을 열 필요가 없게, 참조와 필요한 정보를 문서 안에 묶는다 (「한 장으로 묶기」).

## 입력과 출력

- 입력: `sdd:draft` 가 쓴 `requirements.md` 하나
- 출력: 입력과 같은 폴더의 파일 하나
    - `sdd:brief-dev` → `brief-dev.md`
    - `sdd:brief-nondev` → `brief-nondev.md`
- 폴더 고르기와 덮어쓰기 확인은 `spec-format.md` 「저장 위치」를 따른다
- 마스터가 요청하기 전에는 커밋하지 않는다

## 변환 원칙

- 입력 문서의 모양을 그대로 둔다
    - 제목, 기준 날짜·작성자 줄, 헤딩 이름과 단계. 절 순서만 「절 순서」를 따른다
    - 요구사항 번호, 인수 조건 번호와 개수, 결정 ID
    - 표, mermaid 그림, 공유 문서에서 옮겨 온 `[embedded content: …]` 자리
    - 「결론 / 필요한 결정」 같은 결론·요약 블록이 있으면 그대로 옮기고, 없으면 없는 그대로. 둘지 말지는 brief 가 정하지 않는다
- 내용을 더하지 않는다
    - 새 조사, 새 결정, 새 절, 새 예시, 이야기·인물·유저시나리오를 넣지 않는다
    - 예외는 「한 장으로 묶기」 하나다. 용어 뜻과 다른 문서의 요구사항·결정은 바깥 문서에 이미 있는 것을 옮길 뿐이라 새 조사나 새 결정이 아니다
    - 결정마다 `예시:` 줄을 새로 붙이지 않는다. 예시는 입력에 있는 자리 하나에만 둔다 (`spec-format.md` 「한 번만 쓴다」)
    - 그림이 없으면 그림을 새로 그리지 않는다
- 내용을 빼는 것은 아래 「한 장으로 묶기」(링크와 로컬 파일 경로), 「날짜와 회의 출처」, 「마커 제거」, 「개발 언어 순화」가 정한 것, 그리고 「참여자별 검토 기록」 절뿐이다. 이 절은 `sdd:persona-review` 가 다시 검토할 때 쓰는 LLM 용 기록이라 brief 로 옮기지 않는다 (`references/persona-review.md` 「검토 기록」)
- 문장을 나누거나 합치지 않는다. 한 줄은 한 줄로 바꾼다. 링크가 끊겨 어색해진 문장은 「본문 링크 지우기」대로 최소한만 고친다
- 마스터 답 원문(`"…"` 로 인용한 말)은 두 버전 모두 한 글자도 바꾸지 않는다

## 절 순서

두 버전 모두 같다. 말뜻과 주체를 먼저 알고 요구사항을 읽은 뒤, 결정과 맞닿는 곳을 보게 한다.

- 제목, 기준 날짜·작성자 줄
- `## 도메인 언어`
- `## 주체`
- `## 요구사항` (그 아래 `### 요구사항 {n}` 전부)
- 한 줄 `---`
- 나머지 절. 「결론 / 필요한 결정」, 「필요한 결정 상세」, 「기존 시스템과 맞닿는 곳」 같은 절을 입력에 있던 순서대로 둔다
- `## 다른 문서에서 가져온 내용`. 가져올 것이 있을 때만 맨 끝에 둔다

지키는 것

- 입력에 없는 절은 건너뛴다. 「주체」가 없으면 「도메인 언어」 다음이 「요구사항」이다
- 도메인 언어·주체·요구사항 사이에 있던 다른 절(예: 「핵심 흐름」)도 `---` 아래로 내려 원래 순서대로 둔다
- `---` 는 코드 블록 밖에 한 번만 쓴다. mermaid 머리말의 `---` 는 그림의 일부라 그대로 둔다
- 절은 통째로 옮긴다. 절 안의 내용 순서와 헤딩 단계는 바꾸지 않는다

## 한 장으로 묶기

두 버전 모두 한다. brief 를 받는 사람은 brief 파일 하나만 받는다. 입력이 가리키는 다른 파일은 열 수 없다. 그래서 바깥 문서에 기대는 뜻과 내용을 문서 안에 옮겨 둔다.

`spec-format.md` 「한 번만 쓴다」와 부딪히지 않는다. brief 는 손으로 고치지 않고 늘 원본에서 다시 만드는 사본이라(「답 반영」), 옮겨 적은 내용이 원본과 따로 고쳐질 일이 없다.

### 바깥 참조 찾기

입력 본문에서 아래를 찾는다. 하나도 없으면 이 절의 나머지는 건너뛴다.

- 대상이 입력 폴더 밖인 마크다운 링크. vault 같은 공통 용어집의 용어·주체·흐름·기준 문서와 문서 지도다 (예: `[제휴가](../vault/제휴가.md)`, `[임직원 할인](<../vault/임직원 할인.md>)`)
- 입력에 `### 요구사항 {n}:` 헤딩이 없는 요구사항 번호와 그 조건 번호 (예: "요구사항 4 조건 7(제휴카페)"). 입력 안의 요구사항을 가리키는 번호는 바깥 참조가 아니다
- 입력 「결정 기록」 표에도, 「필요한 결정」의 `**A1. …**` 에도 없는 결정 ID (예: 인수 조건 끝의 `(B11)`)
- 저장소 밖 로컬 파일 경로 (예: `~/workspace/vault/스펙/….md`)

### 용어와 주체 풀어 쓰기

「도메인 언어」·「주체」 절의 링크는 링크 대신 `- {용어} — {뜻}` 줄로 그 절 안에 풀어 쓴다.

- 뜻은 링크한 파일의 본문이다. 본문의 표, 하위 불릿, 그림도 함께 옮긴다
- 뜻에서 빼는 것
    - 마커와 「표기:」 줄
    - "넣고 바꾸는 규칙은 요구사항 4(제휴카페)에 있습니다" 처럼 다른 곳을 안내하기만 하는 문장
    - 파일 안의 링크. 링크 글자만 남긴다
- 문서에서 쓰는 것만 옮긴다. 용어집에 있어도 입력이 쓰지 않는 용어는 옮기지 않는다
- 입력이 묶은 무리(예: 가격과 할인, 정산)는 `**{무리 이름}**` 굵은 줄 아래에 그대로 묶는다
- 흐름·기준 문서(예: 「돈의 흐름」, 「날과 달의 기준」, 「제휴카페 목적과 원칙」)도 용어처럼 풀어 쓴다
- 「주체」 절의 줄(예: "시스템: 아란테운영자 — 사용액 표를 보고 수기로 청구·보전")은 그대로 두고, 주체마다 뜻을 같은 절 안에 둔다
- 같은 파일을 두 절이 가리키면(예: 임직원) 뜻은 한 곳에만 쓰고, 다른 곳은 그 절을 가리킨다
- 문서 지도 링크는 풀어 쓰지 않는다. 문서 지도는 「다른 문서에서 가져오기」에서 출처를 찾는 데만 쓴다
- 뜻풀이에도 「날짜와 회의 출처」와 「마커 제거」를 적용한다. `sdd:brief-nondev` 는 「개발 언어 순화」도 적용한다
- 파일이 없거나 열리지 않으면 짐작해서 채우지 않는다. 용어 이름만 두고 끝맺음에 "requirements.md 에 정의를 넣을 후보" 로 적는다

### 다른 문서에서 가져오기

다른 문서의 요구사항 번호, 조건 번호, 결정 ID 는 출처를 찾아, 가리킨 부분만 맨 끝 `## 다른 문서에서 가져온 내용` 절에 옮긴다.

- 출처 찾기: 문서 지도(예: 「제휴 문서 지도」)의 표로 그 번호나 ID 가 있는 문서를 찾는다. 문서 지도가 없으면 입력이 이름으로 가리킨 문서를 본다
- 옮길 글
    - 출처 문서 폴더에 같은 종류의 형제 brief 가 있으면 그 문구를 쓴다. `brief-dev.md` 를 쓰면 `brief-dev.md`, `brief-nondev.md` 를 쓰면 `brief-nondev.md` 다
    - 없으면 그 문서의 `requirements.md` 를 이 문서와 같은 변환 규칙으로 바꿔 옮긴다
- 한 단계만 따라간다. 옮긴 글 안에 또 나오는 요구사항 번호·조건 번호·결정 ID 는 따라가지 않고 그대로 둔다
- 찾지 못하면 짐작해서 채우지 않는다. 끝맺음에 "찾지 못한 번호" 로 적는다

절 모양

- 헤딩: `## 다른 문서에서 가져온 내용`. 가져올 것이 없으면 절을 두지 않는다. "해당 없음" 줄도 두지 않는다
- 맨 위: 이 문서가 가리키는 다른 문서의 요구사항과 결정을 옮겼다는 한 줄과, "옮긴 글 안의 다른 번호는 출처 문서에 있습니다." 한 줄
- 요구사항: 출처 문서마다 굵은 줄(예: `**제휴회사 문서의 요구사항**`)로 묶고, 요구사항마다 불릿 하나
    - `- {문서} 요구사항 {n}: {제목}`
    - 그 아래 가리킨 조건만 `- 조건 {k}: {문장}` 불릿으로 둔다. 조건 없이 요구사항만 가리켰으면 사용자 스토리 한 줄을 둔다
    - `{k}. ` 숫자 줄로 쓰지 않는다. 검증의 번호 줄 수가 입력과 달라진다
- 결정: 표 하나. 열은 `| 문서 | ID | 질문 | 마스터 답 | 문서에 반영한 뜻 |` 이다. 출처 「결정 기록」 행을 옮기고, 문서 칸에 출처 문서 이름을 쓴다

### 본문 링크 지우기

- 「도메인 언어」·「주체」 밖의 링크는 지우고 링크 글자(용어, 번호)만 남긴다. `[날과 달의 기준](<../vault/날과 달의 기준.md>)` → 날과 달의 기준
- 링크가 끊겨 어색해지는 문장만 최소한으로 고친다
    - "결정 ID 가 이 문서의 「결정 기록」에 없으면 제휴 문서 지도에서 찾습니다" → "… 없으면 이 문서 맨 끝 「다른 문서에서 가져온 내용」에서 찾습니다"
- "제휴카페 문서(요구사항 4)" 같은 번호 언급은 그대로 둔다. 읽는 사람은 번호로 맨 끝 절을 찾는다

### 코드와 파일 출처

- 코드 경로와 외부 웹 URL: `sdd:brief-dev` 는 출처로 그대로 둔다. `sdd:brief-nondev` 는 「개발 언어 순화」대로 코드를 뺀다
- 저장소 밖 로컬 파일: 경로를 빼고 짧은 출처 이름만 둔다. 파일 내용은 옮기지 않는다
    - "「결제로직 시나리오」(`~/workspace/vault/스펙/261106 제휴카페 결제로직.md`, S01~S30)" → "「결제로직 시나리오」(S01~S30)"

## 날짜와 회의 출처

두 버전 모두 한다. 괄호와 표 칸 안의 날짜·회의 출처는 지우고 결정 ID 만 남긴다. 읽는 사람에게 필요한 것은 어느 결정인지이고, 언제 어느 회의에서 정했는지가 아니다.

- 지우는 것
    - `(11-06 회의 Q13 다안, A16)` → `(Q13 다안, A16)`
    - `(11-03 답 C8)` → `(C8)`
    - `(A13, 2026-11-08)` → `(A13)`
    - 결정 표 질문 칸의 `(11-06 회의)`, `(11-06)` → 지운다. `(11-03, 검토 R2)` → `(검토 R2)`
    - ID 없이 날짜·회의 출처만 있는 괄호는 괄호째 지운다
    - 같은 괄호에 코드 출처가 있으면 날짜만 지운다. `(@사실, origin/main 코드, 2026-11-02)` → dev 는 `(origin/main 코드)`
- 남기는 것
    - 헤딩 (예: `## 결정 기록 (2026-11-02, 11-03)`)
    - 기준 날짜·작성자 줄
    - 업무 예시의 날짜와 시각 (예: "11/30 23:50 결제")
    - 문서를 나눈 내력 같은 본문 문장 (예: "2026-11-08 문서를 나눌 때 …", "11-08 결제 로직 보강은 …")

## 마커 제거

두 버전 모두 한다. 결정의 상태는 마커가 아니라 그 결정이 놓인 절(열린·남은 결정 / 정해진 결정·결정 기록)로 드러난다.

- 지우는 것
    - 마커 낱말: `@결정` `@해석` `@초안` `@미정` `@사실` `@가정` `@확정`
    - 마커에 붙은 날짜: `@확정 (A1, 11-02)` 의 `11-02`
    - 표의 「표기」 열
    - 마커만 설명하는 주석: `(모두 @결정)`, `(@가정 2개)`, `(@초안)`, `(모두 @사실)`
    - 마커만 설명하는 문장: "인수 조건 끝의 표기는 근거…", "아래 표는 같은 내용을 표기와 함께 적은 것입니다" 같은 것. 문장의 나머지 반이 여전히 맞으면 그 반은 남긴다 (예: "괄호 안 ID 는 걸린 결정입니다.")
- 남기는 것
    - 결정 ID: 괄호 하나로 모은다
        - `@확정 (A3, A7)` → `(A3, A7)`
        - `@해석 (A3), 한 잔 기준은 @확정 (A6)` → `(A3, A6)`
        - `@확정 (C2), C3·C5의 수기 처리는 @해석` → `(C2, C3, C5)`
        - ID 없이 마커만 있으면 아무것도 남기지 않는다
    - 마커 괄호 안의 내용 문장: `@가정 (기존 정책이 그대로면 …)` → `(기존 정책이 그대로면 …)`
    - 「표기」 열에 결정 ID 가 있었으면 그 ID 를 같은 행의 뜻·규칙 칸 끝에 `(A1)` 로 옮긴다
    - `@사실 ({경로})` 는 낱말만 지운다. 경로는 dev 에 남고, nondev 에서는 「개발 언어 순화」가 지운다
- 열린 결정의 추천안
    - `@초안 a안 — {근거}` → `추천: a안 — {근거}`
    - `@미정 — {이유}` → `추천 없음 — {이유}`
    - 옵션 줄 안의 `@초안` 은 그 옵션이 추천안이라는 뜻이다 → 줄 끝에 `(추천)`
    - 문장 안의 `(@초안 {내용})` → `(추천: {내용})`
    - 마스터가 "미정으로 두라" 고 답해서 붙은 `@미정 ({날짜} 답: …)` 은 추천이 없다는 뜻이 아니다 → `마스터 답으로 미정 (…)`. 날짜는 「날짜와 회의 출처」대로 지운다. 옵션의 추천 표시는 그대로 둔다
- 정해진 결정의 답
    - `@확정 ({날짜} "{답}")` → `답 "{답}"`. 날짜는 「날짜와 회의 출처」대로 지운다
    - 절을 옮기지 않는다. 「남은 결정」에 이미 정해진 결정이 섞여 있어도 그 자리에 두고 마커만 바꾼다
- 지운 뒤 빈 괄호, 겹친 쉼표, 줄 끝 공백을 정리한다

## 개발 언어 순화

`sdd:brief-nondev` 만 한다. 기준은 "개발자가 아닌 운영 직원이 읽을 수 있는가" 다. 업무 용어는 바꾸지 않는다. 헷갈리면 바꾸지 않는다.

- EARS 문장 → "~하면, ~된다" 문장
    - `WHEN …, THE System SHALL …` → "…하면, …된다."
    - `IF …, THEN THE System SHALL …` → "…이면, …된다."
    - `WHILE …, THE System SHALL …` → "…인 동안에는, …된다."
    - `THE System SHALL …` → "…된다." 또는 "…한다."
    - 한 줄은 한 줄이다. 번호와 개수가 입력과 같다. 둘째 문장이 있으면 같은 줄에 둔다
- 지우는 것
    - 코드 경로, 파일 이름, 테이블·컬럼 이름, API·핸들러 이름, 백틱으로 감싼 코드 조각
    - 코드 근거 블록 (예전 문서의 "지금 코드에서 확인한 것"). 업무 언어로 쓴 「지금 동작」 블록은 남긴다
    - 「기존 시스템과 맞닿는 곳」 표 칸에 남은 코드 이름과 "코드에서 확인했다" 문장. 첫 문단의 쉬운 설명, 표와 헤딩, 업무 언어로 쓴 지금 동작, 이번 범위 밖은 남긴다
    - `@사실` 뒤의 출처 괄호 (예: "(origin/main 코드, 2026-11-02)")
    - 코드 조각을 지우면 반쪽이 남는 문장은 쉬운 반만 남긴다
    - 지운 블록을 가리키는 말 (예: "(아래 「지금 코드에서 확인한 것」 때문)")
- 바꾸는 말 (개발자만 읽는 말)
    - `M:N` → "여러 회사와 여러 카페를 서로"
    - "어드민" → "관리자 화면"
    - "(소프트 삭제)" 처럼 앞 문장을 개발 용어로 다시 부른 괄호 → 지운다
    - 문장 안의 "소프트 삭제" → "지우지 않고 남겨 두기" (그 기능의 업무 이름이 있으면 그 이름, 예: "퇴사 처리")
    - "피벗" → "묶어 보기" (예: "회사별·카페별로 묶어 볼 수 있게")
    - "레코드", "행" → "기록", "줄"
- 바꾸지 않는 말
    - 「도메인 언어」·「주체」 절의 용어 이름 전부. 풀어 쓴 뜻풀이는 이 절의 규칙대로 쉬운 말로 바꾼다
    - 업무 용어: POS, 키오스크, 정산, D+6, KST, 선결제, 쿠폰, 스탬프, 세금계산서, 정가, 제휴가, 도메인(이메일 @ 뒤쪽) 같은 것
    - "LLM", "마스터": 마스터가 정한 호칭이다
    - 마스터 답 원문 (`"소프트딜리트"`, `"피봇팅"`, `"2-depth"` 처럼 개발 용어가 들어 있어도)
    - 금액, 날짜, 시각, 예시 숫자

## 답 반영

brief 문서는 답을 갖지 않는다.

- 마스터가 brief 를 보고 "A8. a" 처럼 답하면, `sdd:draft` 「답 반영」으로 `requirements.md` 를 고친 뒤 brief 를 다시 만든다
- 쉬운 말 점검에서 뜻이 정의되지 않은 말이 나오면 brief 에 정의를 더하지 않는다. 끝맺음에 "requirements.md 「도메인 언어」에 넣을 후보" 로 적는다
- brief 를 손으로 고치지 않는다. 다음에 다시 만들 때 사라진다
