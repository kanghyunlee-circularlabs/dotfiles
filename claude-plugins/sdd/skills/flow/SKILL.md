# sdd:flow — 와이어프레임 전의 화면흐름 문서

요구사항 문서를 받아 "어느 화면에 무엇이 끼어들고, 그 값을 무엇으로 정하는가" 를 `flow.md` 로 쓴다. pug-frame 와이어프레임은 그리는 데 시간이 많이 들고, 값의 정의가 어긋나도 다 그린 뒤에야 드러난다. 그 전에 흐름도와 화면 표로 먼저 맞춰 보게 하는 것이 목적이다. 코드와 와이어프레임 파일은 바꾸지 않는다.

먼저 `${CLAUDE_PLUGIN_ROOT}/references/spec-format.md` 와 `${CLAUDE_PLUGIN_ROOT}/references/flow.md` 를 읽는다. 결정·마커·답 반영은 앞 문서를, 그리는 범위·흐름도·화면 표·완성 조건은 뒤 문서를 따른다. 이 스킬은 "문서를 어떤 순서로 쓰는가" 만 정한다.

- `sdd:draft`: 요구사항 문서(무엇을). 이 스킬의 입력이다
- `sdd:design`: 기능명세서(어떻게). 저장 뒤 처리 순서, 기록, API 는 거기서 다룬다. 이 스킬은 design.md 가 없어도 쓴다
- `pug-frame`: 이 문서가 「완성」 된 뒤 와이어프레임을 그리는 스킬

## 입력 찾기

- spec-format 「저장 위치」의 「폴더 고르기」로 폴더를 정하고, 그 안의 `requirements.md` 를 입력으로 쓴다. 고른 폴더에 `requirements.md` 가 없으면 쓰지 않고 "`/sdd:draft` 를 먼저 실행하세요" 한 줄을 남긴다
- 설명에 요구사항 문서가 둘 이상 있으면(예: 「제휴카페」와 「제휴결제」) 모두 읽는다. 저장 폴더는 첫 문서의 폴더다
- 설명에 와이어프레임·스토리보드 파일 경로가 있으면 함께 읽는다. 그때만 「와이어프레임에서 고칠 곳」을 쓴다
- 문서를 끝까지 읽는다. 앞부분만 보고 쓰지 않는다
- 요구사항 문서에 `(작성 중)` 이 남아 있으면 쓰지 않고, 그 절 이름을 알려 준다
- 요구사항 문서의 「열린 결정」이 남아 있어도 멈추지 않는다. `references/flow.md` 「결정 표기」대로 추천안으로 그린다

## 범위 정하기

- 요구사항 문서의 참여자(주체)와 와이어프레임 파일 이름에서 화면 묶음(한 주체가 쓰는 한 앱)을 뽑는다. 화면에 보이는 인수 조건이 없는 주체(배치, 외부 연동)는 묶음이 아니다
- 설명에 화면 묶음 이름이 있으면 그 묶음만 쓴다
- 없으면 모든 묶음을 쓴다. 묶음이 4개 이상이면 걸린 인수 조건이 가장 많은 묶음 하나만 쓰고 나머지는 「다음 차례」에 둔다. 한 번에 검토할 흐름도를 줄이기 위해서다
- 이미 있는 `flow.md` 에 다음 묶음을 더할 때는 `## {화면 묶음}` 절을 더하고 「다음 차례」에서 그 줄을 지운다

## 저장 위치

- 요구사항 문서와 같은 폴더의 `flow.md`. 나머지는 spec-format 「저장 위치」를 따른다
- 설명에 저장 경로가 있으면 그 경로에 쓴다 (예: Obsidian 스토리보드 폴더). 그 폴더가 worktree 밖이어도 마스터가 그 폴더만 열어 보기 때문에 그대로 쓴다
- 마스터가 요청하기 전에는 커밋하지 않는다

## 조사 (AS-IS)

흐름도의 회색 노드와 화면 글자는 지금 화면에서 가져온다. 아래 순서로 찾는다.

- 와이어프레임 파일: 화면 이름, 탭 이름, 다이얼로그 이름
- 지금 리포에 그 앱의 코드가 있으면 `git fetch` 후 `origin/main` 기준으로 라우트, 사이드바 메뉴, 다이얼로그 컴포넌트를 읽는다 (`git grep … origin/main`)
- 요구사항 문서의 「기존 시스템과 맞닿는 곳」
- 어디서도 확인하지 못한 화면 이름은 짐작해 쓰고, 그 행 근거 칸에 `@가정` 을 붙인다

## 쓰는 순서

- **뼈대 먼저.** Write 로 제목, 기준 줄, `references/flow.md` 「문서 구성」의 `##` 헤딩, 절마다 `(작성 중)` 한 줄을 만든다. 쓰기 전에 채팅에 "{경로}에 씁니다" 한 줄을 남긴다
- 「조사 (AS-IS)」를 한다
- 화면 묶음마다
    - 화면 표를 먼저 채운다. 값과 조건은 표 한 곳에만 있으므로 표가 흐름도의 원본이다
    - 표를 보고 흐름을 하나씩 그린다. 흐름 하나를 그릴 때마다 채팅에 "지금 {흐름} 작성 중" 한 줄을 남긴다
    - 「경로」를 그린다
    - 와이어프레임을 받았으면 「와이어프레임에서 고칠 곳」을 채운다
    - 「범위 밖」을 채운다
- 요구사항 문서에서 화면에 보이는 동작을 정한 인수 조건을 하나씩 세어, 어느 표의 근거 칸이나 「범위 밖」에도 없는 것이 있으면 그 화면으로 돌아간다
- 「필요한 결정」은 마지막에 채운다
- 「흐름도 확인」을 한다
- `(작성 중)` 이 남았는지 검색해 없앤다
- spec-format 「윤문」을 거친다. 대상 목록에 `flow.md` 가 있다

## 흐름도 확인

- 흐름도마다 저장 뒤 서버 처리(검증 순서, 기록, API)를 그린 노드가 있는지 본다. 있으면 지우고, 그 결과로 사용자가 보는 화면 상태만 남긴다
- 노드마다 `:::asis`·`:::add`·`:::mod` 가 붙었는지, 흐름도마다 `classDef` 세 줄이 있는지 본다
- mermaid-cli 로 문서를 그려 본다. 오류가 나면 고치고 다시 그린다
    - `npx -y -p @mermaid-js/mermaid-cli@11.4.2 mmdc -i {flow.md} -o {스크래치 폴더}/flow-check.md`. 버전을 고정한 것은 최신 버전이 브라우저(chrome-headless-shell)를 따로 깔아야 돌아가기 때문이다
    - 만들어진 SVG 는 스크래치 폴더에만 두고 스펙 폴더에 남기지 않는다
    - mermaid-cli 를 돌릴 수 없으면(네트워크, 브라우저 없음) 끝맺음에 "흐름도를 그려 보지 못했습니다" 한 줄을 붙인다

## 답 반영

spec-format 「답 반영」대로 같은 문서를 고친다. 새 문서를 만들지 않는다. 고친 뒤 「흐름도 확인」과 spec-format 「윤문」을 다시 거친다. 다른 점만 적는다.

- 답은 두 군데서 온다: 채팅의 "M1. a", 문서의 결정 제목 `->` 옆. 둘 다 읽는다
- 마스터가 옵션이 아닌 새 화면 구성을 제안하면(예: "정산 명세에는 열만 추가하고, 제휴정산 탭을 따로 둬라") 다음 번호의 결정으로 「정해진 결정」에 원문을 넣고, 그 제안으로 바뀐 이전 결정에 `(M4로 바뀜)` 을 붙인다
- 답 때문에 지워진 화면 요소는 표와 흐름도에서 모두 지운다. 와이어프레임을 받았으면 지워진 시나리오를 「와이어프레임에서 고칠 곳」에 삭제 행으로 더한다
- 요구사항 문서가 바뀌면 바뀐 번호를 근거 칸에서 찾아 걸린 화면만 고친다

## 끝맺음

- 첫 줄
    - `references/flow.md` 「완성」이면: "완성 — 와이어프레임을 그릴 수 있습니다." 와 다음 행동 한 줄 (와이어프레임을 받았으면 「와이어프레임에서 고칠 곳」 반영, 아니면 `pug-frame` 으로 새로 그리기)
    - 아니면: 다음에 답할 결정 하나. 구체 예시와 추천안을 붙인다
- 둘째 줄: 문서 경로(클릭 가능한 `path`)
- 무엇을 썼는지·바꿨는지 불릿 5개 이하. 화면 수, 흐름도 수, 렌더링 확인 결과를 포함한다. 문서 내용을 다시 늘어놓지 않는다
- 역반영 제안이 있으면 요구사항 문서에 올릴 문장을 한 줄씩, 3개 이하
- 「다음 차례」가 남았으면 다음 묶음과 명령 한 줄 (예: `/sdd:flow {폴더} 임직원 웹오더`)

## 하지 않는 것

- 코드를 바꾸지 않는다
- 요구사항 문서를 고치지 않는다. 역반영은 제안만 하고, 반영은 `sdd:draft` 의 「답 반영」이 한다
- 와이어프레임 파일을 고치지 않는다. 고칠 곳은 목록으로만 남긴다
- pug-frame 을 그리지 않는다
- 저장 뒤 서버 처리 순서, 기록, API 를 흐름도나 표에 쓰지 않는다
- 요구사항 문서의 규칙·수치를 옮겨 적지 않는다
