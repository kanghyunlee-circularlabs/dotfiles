## 판정 요약

다음 달에 다시 이 작업을 할 때는 이 요약을 근거로 쓰지 말고, 그때의 원문을 처음부터 다시 읽어라. 이 목록에 새 프롬프트를 배정하기 시작하면 추상화가 유실된다.

새 스킬이 필요한 것

- 구현을 서브에이전트에 넘기고 검수만 한다 — 6건 / 6세션. 우선순위 1위
- 실패한 실행의 로그를 던지고 원인을 규명한다 — 15건 / 11세션. 우선순위 2위
- 설계안을 던지고 트레이드오프를 받는다 — 14건 / 11세션. 우선순위 3위
- 자기 동작을 스스로 확인한다 — 15건 / 13세션. 스킬 대신 프로브 스크립트일 수 있다
- 브랜치를 main 최신으로 맞추고 충돌을 푼다 — 6건 / 6세션. 규칙 한 줄로 갈음할 수 있다

이미 있는데 안 쓰이는 것

- 계획서만 받는다 — `/wt:plan`. 16일간 0회. `claude-plugins/wt/` 에 `skills/` 가 없어서 자연어로 안 잡힌다
- 브랜치 따서 PR 올린다 — `/wt:init`. 16일간 1회. 원인 같음
- 문서를 코드 실제와 대조해 보강한다 — `wiki-refiner`. 16일간 0회. `~/.claude/commands/` 라 원인 같음. 범위도 좁다
- 에이전트 자신의 설정을 고친다 — `skill-creator`, `update-config`. 둘 다 0회

여기서 상관관계가 하나로 모인다. **커맨드로만 만든 것은 안 불리고, 스킬로 만든 것은 불린다.** `side-issue`(스킬) 10회, `roguelike`(스킬) 사흘 만에 2회에 견줘 `wt:plan`·`wiki-refiner`·`plan-issue`(전부 커맨드) 는 0회다.

다만 처방까지 하나로 모이지는 않는다. `wt` 는 자연어 발동이 오작동해서 **일부러** 커맨드로 옮긴 것이고(README 근거), `wiki-refiner` 와 `plan-issue` 는 애초에 이 리포지토리에 존재하지 않는다(`configs/claude/` 에 `commands/` 디렉터리가 없다). 셋의 처방이 각각 다르다. "어디에 넣을 수 있나" 절에 갈라 적었다.

스킬로 만들 값어치가 없는 것

- 외부 문서를 근거로 구현물을 만든다 — 대상이 제각각이다. 대신 한 번 읽은 외부 문서를 리포지토리에 남기는 습관 문제다
- 도메인 규칙이 코드에서 실제로 어떻게 도는지 확인한다 — 그냥 코드 읽기다
- 이슈·PR 번호만 주고 착수한다 — 입력 관습이지 행위가 아니다
- 머지 상태를 정리한다 — 단발 git 조작이다

## 어디에 넣을 수 있나

`claude-plugins/` 6개와 `configs/claude/skills/` 3개를 전부 열어보고, 각 후보를 어디에 놓을 수 있는지 검사했다.

### 지금 있는 자리

플러그인 6개의 구성은 이렇다. 빈칸이 곧 넣을 수 있는 자리다.

- `aol` — 훅만 있다. `commands/` 없음, `skills/` 없음
- `gnothi` — 훅 + `commands/setup.md`. `skills/` 없음
- `wt` — `commands/{init,plan,clean}.md` + `references/common.md`. `skills/` 없음
- `side-issue` — `skills/side-issue/` + `commands/prerequisite.md`. 스킬과 커맨드를 둘 다 가진 유일한 예다
- `socrates` — `skills/{socratic-tutor,socratic-record}/` + `commands/scrt.md`
- `notion-po` — `skills/` 4개 + `commands/po.md`

개인 스킬 `configs/claude/skills/` 에는 셋이 있다. `pug-frame`(DSL 문법), `qa`(계획자 세션에 물으며 실행), `roguelike`(세션 넘기기). 뒤의 둘은 **세션을 다루는 스킬**이라는 공통점이 있고, 리포지토리에 매이지 않는다.

그리고 `configs/claude/` 에는 `rules/markdown.md` 한 장이 있다. `scripts/rules-inject.py` 가 auto 모드에서 Bash 로 만진 파일 경로까지 훑어 규칙을 다시 넣어주므로, 규칙 파일은 실제로 작동하는 경로다.

### 리포지토리에 없는 것 — plan-issue, wiki-refiner

`configs/claude/` 에 `commands/` 디렉터리가 **아예 없다.** `plan-issue` 와 `wiki-refiner` 는 `~/.claude/commands/` 에만 있고 리포지토리에는 없다. 앞 절에서 이 둘을 "이미 있는데 안 쓰임" 으로 판정했는데, 정확히는 **이 머신에만 있고 리포지토리에 없다.** 재현가능한 환경을 목적으로 하는 리포지토리에서 이건 결손이다.

`configs/claude/commands/` 를 만들어 둘을 옮기는 것이 먼저다. 그래야 "왜 안 불리나" 를 따질 대상이 된다. 지금은 다른 머신에서는 존재하지도 않는다.

### 후보별 배치안

**구현을 서브에이전트에 넘기고 검수만 한다 → `configs/claude/skills/`**

`qa`, `roguelike` 와 같은 계열이다. 셋 다 "세션을 어떻게 굴릴 것인가" 를 다루고 특정 리포지토리에 매이지 않는다. 훅도 커맨드도 필요 없고 `SKILL.md` 한 장이면 된다. `qa` 가 정확히 그 모양으로 슬래시와 자연어를 둘 다 받고 있다.

`side-issue` 플러그인에 넣는 안도 검토했는데 맞지 않는다. `side-issue` 는 `--fork-session` 으로 **컨텍스트를 물려주는** 방식이고, 이 후보는 반대로 **자기완결적 지시문으로 직렬화해서 넘기는** 방식이다. 마스터 프롬프트가 매번 "완결된 지시문", "자기완결적으로 instruction" 이라고 못 박는 것이 그 차이다. 한 플러그인에 두면 둘이 섞인다.

`wt` 반례는 여기 걸리지 않는다. `wt` 가 물린 것은 한 스킬이 모드를 두 개 가져서 어느 쪽인지 추측해야 했기 때문인데, 이 후보는 모드가 하나뿐이다.

**실패한 실행의 로그를 던지고 원인을 규명한다 → `configs/claude/skills/` 로 시작**

`gh run view`, `act`, CloudWatch 를 다루고 절차가 길어서 나중에 `references/` 가 필요해질 수 있다. 그때 `claude-plugins/` 로 올리면 된다. `wt` 가 밟은 경로가 그것이다 — `configs/claude/skills/wt/SKILL.md` 로 시작해 09-10 에 플러그인이 됐다.

`side-issue` 플러그인에 넣는 안은 경계를 넘는다. 그 플러그인의 책임은 이슈화이지 원인 규명이 아니다. 대신 스킬 본문 끝에서 `/side-issue` 를 부르면 된다. `side-issue` 는 스킬이라 자연어로도 잡힌다.

**설계안을 던지고 트레이드오프를 받는다 → `configs/claude/skills/`**

`configs/claude/rules/` 에 규칙으로 넣는 안을 먼저 검토했는데 맞지 않는다. 규칙 파일은 `paths` frontmatter 로 특정 파일에 걸리는 구조인데, 이 행위는 파일과 무관하다. `rules-inject.py` 도 Bash 커맨드에 나온 **파일 경로**를 매칭하는 것이라 같은 한계를 갖는다.

스킬이 맞다. CLAUDE.md "복수안, 그리고 불가 금지" 절이 이미 산출물 형식을 정해뒀으니(2~3안, 장단점, 예상 비용, 리스크, 되돌림 가능 여부, 성공 판단 기준, 의사결정 시한) 스킬은 그 형식을 강제하는 얇은 껍데기면 된다.

**자기 동작을 스스로 확인한다 → `claude-plugins/gnothi/commands/`**

여기는 자리가 정확히 맞는다. `gnothi` 의 책임이 바로 session_id·model·rules 주입이고, `/gnothi:setup` 이 이미 "훅이 실제로 동작하는지 파이프 테스트로 확인한다" 를 하고 있다. 검증 대상과 검증 도구가 같은 플러그인에 있게 된다.

스킬이 아니라 **커맨드**여야 한다. 이건 마스터가 명시적으로 부르는 검증이고, 자연어로 잡히면 일반 대화에서 오발동한다. `wt` 가 물린 것과 같은 함정이다. 프롬프트 원문도 `Do not use any tools. ... Answer YES or NO only.` 처럼 이미 커맨드에 가깝다.

**브랜치를 main 최신으로 맞추고 충돌을 푼다 → `configs/claude/rules/` 또는 CLAUDE.md**

`wt` 에는 넣을 수 없다. `wt` 는 "어느 커맨드도 코드는 손대지 않는다" 가 명시적 계약인데, 충돌 해결은 코드를 고친다. `references/common.md` 에도 "코드 파일은 두 커맨드 모두 수정하지 않아요" 로 못 박혀 있다.

6건이고 절차가 짧으니 규칙 한 줄이 싸다. CLAUDE.md 형상관리 절에 "충돌 해결은 양쪽 변경의 의도를 먼저 적고 시작한다" 정도면 된다. 스킬을 새로 파는 것은 값어치에 비해 비싸다.

**계획서만 받는다 / 브랜치 따서 PR 올린다 → `claude-plugins/wt/skills/` (조건부)**

`skills/` 자리는 비어 있다. 다만 앞서 적은 대로 예전 `wt` 스킬이 모드를 추측하다 물렸으므로, 그 모양 그대로 되돌리면 안 된다.

- 추측하지 않는 얇은 디스패처 — "계획", "PR 올려" 같은 말이 오면 어느 커맨드인지 **묻고**, 답을 받아 해당 커맨드 절차로 넘긴다. 물어보는 비용 한 번이 빈 PR 을 올리는 비용보다 싸다
- 아니면 스킬을 안 만들고 CLAUDE.md 에 유도 한 줄 — "계획만 원하면 `/wt:plan`, 작업 시작만 원하면 `/wt:init`". 되돌리기 가장 쉽다

둘 중 무엇이든 되돌리기 쉬우니 값싼 쪽부터 해보는 편이 낫다. 마스터 판단이 필요하다.

**이 리포트를 만드는 작업 자체 → `claude-plugins/aol/commands/`**

`aol` 은 로그를 **쌓기만** 하고 읽는 쪽이 없다. `commands/` 도 `skills/` 도 없다. 이번 세션이 한 일(프롬프트 전부 읽고 아래에서 위로 묶기)은 매달 반복될 일이고, 절차도 이미 이 문서에 다 적혀 있다.

커맨드여야 한다. 매달 한 번 마스터가 작정하고 부르는 일이지, 대화 중에 자연어로 튀어나올 일이 아니다. 그리고 커맨드 본문에 "분류 체계를 먼저 만들지 않는다" 를 못 박아 둘 수 있다. 이 제약은 세션이 바뀔 때마다 잊히기 쉬운데, 커맨드에 적어두면 매번 따라온다.

### 정리

- `configs/claude/skills/` — 서브에이전트 위임, 실패 로그 원인 규명, 트레이드오프. 셋 다 `SKILL.md` 한 장으로 시작
- `claude-plugins/gnothi/commands/` — 자기 동작 프로브
- `claude-plugins/aol/commands/` — 프롬프트 채굴(이 리포트를 만드는 일)
- `claude-plugins/wt/skills/` — 조건부. 모드를 묻는 디스패처만. 추측하면 안 된다
- `configs/claude/rules/` 또는 CLAUDE.md — 충돌 해결
- `configs/claude/commands/` — 새로 만들어 `plan-issue`, `wiki-refiner` 를 리포지토리로 들이기
